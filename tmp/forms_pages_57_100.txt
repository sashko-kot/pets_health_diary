5.3. Создание форм на основе моделей (ModelForm) 
В предыдущих разделах была рассмотрена работа с формами Django на приме-
ре BookingFilterForm. Эта форма предназначена для фильтрации существую-
щих бронирований: она получает параметры из GET-запроса, проверяет их и пере-
даёт представлению значения для формирования выборки. 
Однако при создании и редактировании объектов требуется не только прове-
рить введённые данные, но и сохранить их в базе данных. 
Для этого Django предоставляет класс ModelForm, позволяющий создавать 
формы на основе моделей приложения. 
5.3.1. Назначение ModelForm 
ModelForm – это класс Django, который связывает форму с моделью базы 
данных. При создании обычной формы на основе forms.Form разработчик само-
стоятельно определяет поля формы и при необходимости отдельно реализует сохра-
нение объекта. 
При использовании ModelForm поля формы формируются на основе выбран-
ной модели. После успешной проверки данных форму можно использовать для со-
здания нового объекта или изменения существующего. 
Например, в Roomly модель Booking описывает бронирование и содержит 
сведения о помещении, пользователе, дате и состоянии бронирования. Если созда-
вать форму на основе Booking, Django может сформировать поля для работы с ат-
рибутами модели. Разработчику остаётся определить, какие поля следует показы-
вать пользователю и как обрабатывать отправленные данные. 
Основные преимущества ModelForm: 
 автоматическое создание полей на основе модели; 
 использование правил валидации, заданных моделью; 
 преобразование введённых значений в соответствующие типы Python; 
 проверка корректности данных перед сохранением; 
 возможность создавать новые объекты и редактировать существующие; 
 сокращение объёма повторяющегося кода. 
При этом ModelForm не заменяет представление и шаблон. Форма отвечает за 
поля и проверку данных, представление организует обработку запроса, а шаблон 
определяет внешний вид формы.

5.3.3. Как ModelForm связана с моделью 
Чтобы создать ModelForm, необходимо указать модель, на основе которой 
формируется форма. Это делается внутри вложенного класса Meta. 
Рассмотрим общий пример: 
from django import forms 
from bookings.models import Booking 
class BookingForm(forms.ModelForm): 
    # Внутренний класс с настройками формы. 
    class Meta: 
        # Указываем модель, с которой связана форма. 
        model = Booking 
        # Перечисляем поля модели, которые должны отображаться в фор-
ме. 
        fields = [ 
            "room", 
            "booking_date", 
            "user", 
        ] 
Разберём основные элементы кода. 
 forms.ModelForm – базовый класс для создания форм на основе моделей 
Django. 
 BookingForm – класс формы, который будет использоваться в представлениях. 
 class Meta – внутренний класс, содержащий настройки формы.

---PAGE 59---
59 
 model = Booking – указывает Django, на основе какой модели формировать по-
ля. 
 fields – определяет список полей модели, доступных для редактирования через 
форму. 
В данном примере перечислены поля помещения, даты и пользователя. Django 
сформирует для них соответствующие элементы формы. 
Список fields необходимо определять явно. Не следует без необходимости 
использовать fields = "__all__", поскольку при добавлении новых полей моде-
ли они могут автоматически попасть в форму, даже если их не следует показывать 
пользователю. 
Например, поле status не обязательно предоставлять пользователю при со-
здании бронирования: начальное состояние может определяться логикой приложе-
ния. 
Важно: приведённый код пока является учебным примером структуры ModelForm. Перед 
включением его в проект необходимо проверить фактические имена полей модели Booking и 
определить, какие поля должны быть доступны при создании бронирования. 
5.3.4. Как работает ModelForm при обработке данных 
Работа с ModelForm обычно состоит из нескольких этапов: 
1. Представление создаёт экземпляр формы. 
2. Пользователь заполняет поля и отправляет форму. 
3. Представление передаёт отправленные данные в форму. 
4. Метод is_valid() запускает проверку данных. 
5. Если проверка пройдена, метод save() создаёт или обновляет объект модели. 
6. Представление определяет дальнейшее действие, например перенаправляет поль-
зователя на страницу списка бронирований.

Метод is_valid() не сохраняет объект. Он только проверяет данные и под-
готавливает их для дальнейшего использования. 
Метод save() сохраняет объект, если форма успешно проверена. Поэтому пе-
ред вызовом save() необходимо убедиться, что is_valid() вернул True. 
5.3.5. Создание и редактирование объектов 
ModelForm позволяет работать как с новыми объектами, так и с уже суще-
ствующими. 
Создание нового объекта 
Если форма создаётся без существующего экземпляра модели, после успешной 
проверки вызов save() создаёт новую запись: 
# Создаём форму на основе отправленных пользователем данных. 
form = BookingForm(request.POST) 
# Проверяем корректность данных. 
if form.is_valid(): 
    # Создаём новый объект Booking и сохраняем его в базе данных. 
    booking = form.save() 
Редактирование существующего объекта 
Если необходимо изменить существующее бронирование, в форму передаётся 
объект модели: 
# Получаем существующее бронирование по идентификатору. 
booking = get_object_or_404(Booking, pk=booking_id) 
# Создаём форму с данными запроса и существующим объектом. 
form = BookingForm(request.POST, instance=booking) 
# Проверяем корректность введённых данных. 
if form.is_valid(): 
    # Обновляем существующий объект и сохраняем изменения. 
    booking = form.save() 
Параметр instance указывает, с каким объектом модели связана форма. 
Если instance не передан, save() создаёт новый объект. Если передан су-
ществующий объект, save() обновляет его. 
Приведённые фрагменты показывают общий принцип работы. Представления 
создания и редактирования будут реализованы отдельно после подготовки формы и 
определения допустимых полей.

Шаг 3. Разберитесь, как Django обрабатывает ошибки формы 
Если пользователь отправил некорректные данные, метод is_valid() вернёт 
False. В этом случае выполнение не перейдёт к form.save(). Представление 
дойдёт до render() и снова отобразит форму. При этом Django сохранит: 
 введённые пользователем значения; 
 ошибки отдельных полей; 
 общие ошибки формы. 
Поэтому повторно создавать пустую форму при ошибочной отправке не требу-
ется. Например, если пользователь не выбрал помещение или указал некорректную 
дату, форма будет отображена повторно с соответствующими сообщениями об 
ошибках. 
Шаг 4. Проверьте логику сохранения и связи объектов 
Поскольку Booking связан с моделями Room и User, при сохранении формы 
Django должен получить корректные объекты связанных моделей. Если в 
BookingForm включены поля room и user, Django формирует поля выбора свя-
занных объектов на основе соответствующих QuerySet. При успешной валидации 
в form.cleaned_data находятся не просто идентификаторы, а экземпляры свя-
занных моделей. Например: 
 form.cleaned_data["room"] – объект Room; 
 form.cleaned_data["user"] – объект User. 
Если поле user не включено в форму, его значение необходимо определить на 
стороне сервера до сохранения. В таком случае используется commit=False:

booking = form.save(commit=False)

Шаг 5. Учтите правило доступности помещения

5.4.1. Принцип использования instance в ModelForm 
Параметр instance позволяет указать объект модели, с которым должна ра-
ботать форма. 
При создании объекта используется: 
# Создаём пустую форму для нового бронирования. 
form = BookingForm() 
При редактировании: 
# Создаём форму на основе существующего бронирования. 
form = BookingForm(instance=booking) 
Django автоматически подставляет в поля формы значения из объекта 
booking. 
Например, если у существующего бронирования помещение – «Аудитория 
301», а дата – 15 ноября, эти значения будут отображены в соответствующих полях. 
При отправке формы методом POST: 
# Создаём форму на основе отправленных данных 
# и связываем её с существующим объектом. 
form = BookingForm(request.POST, instance=booking) 
Если форма проходит проверку и вызывается: 
# Сохраняем изменения существующего бронирования. 
form.save() 
Django обновляет существующую запись, а не создаёт новую. 
Важно: instance определяет, какой объект изменяется. Без него form.save() создаст новый 
объект, даже если пользователь фактически редактировал данные существующего бронирования.

# Исключаем из проверки редактируемое бронирование. 
.exclude(pk=booking.pk) 
Почему это необходимо? Представим, что существует бронирование: 
 помещение – «Аудитория 301»; 
 дата – 15 ноября; 
 ID – 5. 
Пользователь открывает его для редактирования, ничего не меняет и нажимает 
кнопку сохранения. Если проверить все активные бронирования без исключения те-
кущей записи, запрос найдёт само редактируемое бронирование. Форма ошибочно 
сообщит, что помещение уже занято. 
exclude(pk=booking.pk) исключает текущую запись из проверки. При 
этом остальные активные бронирования продолжают учитываться. Таким образом: 
 редактируемая запись не блокирует саму себя; 
 другое активное бронирование на ту же дату блокирует сохранение; 
 отменённое бронирование не блокирует помещение. 
Шаг 3. Проверьте повторное использование BookingForm

5.6.2. Настройка хранения загруженных файлов 
В settings.py задайте параметры медиакаталога: 
# URL для обращения к загруженным файлам. 
MEDIA_URL = "/media/" 
# Каталог для физического хранения загруженных файлов. 
MEDIA_ROOT = BASE_DIR / "media" 
В корневом urls.py добавьте обработку медиаданных для режима разработ-
ки: 
from django.conf import settings 
from django.conf.urls.static import static 
# В режиме разработки подключаем раздачу загруженных файлов. 
if settings.DEBUG: 
    urlpatterns += static( 
        settings.MEDIA_URL, 
        document_root=settings.MEDIA_ROOT, 
    ) 
В рабочей среде раздачу медиафайлов обычно настраивают средствами веб-
сервера или отдельного файлового хранилища. 
Примечание. Настройки MEDIA_URL и MEDIA_ROOT, а также подкаталог rooms/ приве-
дены для учебного проекта Roomly. В индивидуальном проекте пути хранения загруженных фай-
лов, имена каталогов и соответствующие настройки необходимо адаптировать к его структуре и 
выбранной сущности.

5.6.4. Передача файла из шаблона в представление 
В HTML-форме обязательно укажите enctype="multipart/form-data": 
<form method="post" enctype="multipart/form-data"> 
    {% csrf_token %} 
    {{ form.as_p }} 
    <button type="submit">Сохранить</button> 
</form> 
Без enctype="multipart/form-data" браузер не передаст файл в ожида-
емом формате. 
В представлении необходимо передать в форму не только request.POST, но и 
request.FILES: 
def room_create(request): 
    if request.method == "POST": 
        # Передаём форме обычные данные и загруженные файлы. 
        form = RoomForm(request.POST, request.FILES) 
        if form.is_valid(): 
            # Сохраняем помещение и загруженное изображение. 
            form.save() 
            return redirect("rooms:rooms") 
    else: 
        # При GET-запросе отображаем пустую форму. 
        form = RoomForm() 
    return render( 
        request, 
        "rooms/room_form.html", 
        {"form": form}, 
    ) 
request.FILES содержит файлы, отправленные пользователем. Django про-
веряет их при валидации формы, а form.save() сохраняет изображение и записы-
вает путь к нему в модель.

5.6.6. Проверка загрузки

1. Откройте форму создания помещения.
